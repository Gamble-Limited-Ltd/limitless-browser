# Speed research: in-page web proxy on a slow Chromebook (2026-11-19)

Method note: web search returned mostly mirrors and third-party blogs; few primary benchmarks exist. Items marked UNVERIFIED rest on a single secondary source or inference.

## 1. How other proxies structure rewriting and transport

- Scramjet (Mercury Workshop): JS rewriter is a Rust/WASM core using the OXC parser (AST transforms), wrapped by a TS layer for error recovery and sourcemaps. HTML rewriter uses htmlparser2 in JS, not WASM. Config (codec, flags) stays in JS so no WASM rebuild is needed. WASM binary is fetched at SW startup. https://www.mintlify.com/mercuryworkshop/scramjet/advanced/rewriters , https://www.mintlify.com/mercuryworkshop/scramjet/advanced/wasm (docs mirror, not the repo)
- Scramjet docs warn URL rewriting "can be expensive for large documents" and expose a `rewriterLogs` flag for timings. https://mintlify.com/mercuryworkshop/scramjet/concepts/url-rewriting
- A March 2026 blog claims "sub-millisecond" rewriting on complex pages. UNVERIFIED, marketing-style, no method given. https://blog.brightcoding.dev/2026/03/21/scramjet-the-revolutionary-web-proxy-with-captcha-support
- Scramjet and Ultraviolet both intercept in a service worker (SW) and pair with a transport (Bare, or libcurl.js/epoxy over Wisp). Ultraviolet rewrites client-side in the SW; the "client-side offloads the server" speed claim is an assertion, not measured. https://github.com/titaniumnetwork-dev/Ultraviolet/ , https://awesome.ecosyste.ms/projects/github.com%2Fcrllect%2Fhow-to-make-an-ultraviolet-proxy
- Rammerhead rewrites server-side (remote browser-like session, own worker code). No throughput numbers found. https://pixelscan.net/blog/rammerhead-proxy-how-it-works/ (third-party explainer)
- Wisp implementations: wisp-js client+server (JS), epoxy-server and wisp-mux (Rust), Woeful (C++), wisp-server-python. Ultraviolet can use libcurl.js or epoxy as transport. https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md
- lol-html (streaming, DOM-less, single pass, memory = open-element depth) has WASM builds usable in browsers: deno-lol-html and worker-tools/html-rewriter (WASM port of the HTMLRewriter API). The wasm build lacks the Cloudflare `transform()`, so you pipe chunks via write()/end() and enqueue output into a ReadableStream. https://deno.land/x/lol_html@0.1.0/README.md , https://github.com/worker-tools/html-rewriter/blob/v0.1.0-pre.17/README.md
- No public proxy found that uses lol-html in a browser SW. Not verified that Scramjet/UV stream HTML (Scramjet docs say htmlparser2, which supports chunked parsing but I did not confirm they use it that way).
- No published head-to-head benchmarks of any of these proxies found (latency, throughput, first paint). UNVERIFIED for all speed claims.

What this means for us: the field's speed answer is "Rust/WASM JS rewriter (OXC) plus SW interception", not acorn/meriyah in JS. A WASM rewriter is the single biggest lever for the multi-MB bundle cost; measure on the Chromebook before adopting, since WASM startup (fetch + compile) also costs on a slow CPU.

## 2. Streaming HTML in a service worker

- A SW can `respondWith(new Response(readableStream))`; Chrome documents that navigation responses built as streams get the browser's streaming HTML parser, and streaming the whole response performed best in their tests. https://developer.chrome.com/blog/sw-readablestreams
- Chrome notes that content injected after load bypasses the streaming parser and renders slower. Same source.
- Preload scanner scans raw markup ahead of the parser to start fetches; a script injected by client JS is invisible to it. So a rewritten stream that keeps `<script src>`/`<link>` as real tags in the first chunks lets the browser fetch early. https://web.dev/articles/preload-scanner
- Early-flush advice: send the head plus preload hints in the first chunk, confirm in a waterfall that the shell really arrives early. https://frontendchecklist.io/rules/performance/streaming-html
- Pipe pattern with lol-html WASM: rewriter output callback does controller.enqueue; a pump loop reads upstream and calls write(), then end(). https://deno.land/x/lol_html@0.1.0/README.md
- Pitfalls (mostly from HTML spec behaviour, not from one source):
  - Charset: bytes must be decoded before rewriting; a `<meta charset>` can appear late in the first 1024 bytes. Safe approach: use the HTTP Content-Type charset, else buffer the first chunk(s), sniff, then stream. UNVERIFIED as a documented proxy pitfall, standard HTML parsing rules.
  - Chunk boundaries: a tag can split across chunks; a streaming tokenizer (lol-html) handles it, a regex does not.
  - Scripts: classic parser-blocking scripts execute in document order, so rewriting external script URLs to a proxied URL is safe in a stream; inline scripts must be rewritten before they are emitted (cheap if small, costly if multi-MB).
  - document.write in a script can inject markup that bypasses your rewriter; it must be hooked at runtime (a client-side shim). Cloudflare notes document.write can also drive memory use in the parser. https://blog.cloudflare.com/html-parsing-1/
  - Content-Length / Content-Encoding must be dropped from the synthetic response.
- This needs the SW lane (currently off in our app). An in-page iframe cannot stream a blob/srcdoc document: it must be complete first.

What this means for us: the biggest first-paint win (page appears while HTML is still arriving) is only reachable through the SW lane or `document.open/write` into the iframe. A cheaper in-page variant: `iframe.contentDocument.open(); write(chunk)...; close()` with streamed, rewritten chunks. Not verified here that the preload scanner benefits on that path; test it.

## 3. Caching rewritten scripts and V8 code cache

- Chrome has two code-cache levels: in-memory Isolate cache (keyed by source text, ~80% hit rate in the wild) and an on-disk cache managed by Blink, attached as metadata to the HTTP-cache entry of the script URL. Cold run (1st load) stores source, warm run (2nd) compiles and serializes, hot run (3rd) deserializes. https://v8.dev/blog/code-caching-for-devs
- Scripts under 1 KiB of source are not code-cached. Inline scripts are cached only as part of the HTML document resource, tied to the whole document not changing. Only functions compiled by the end of top-level execution are cached (IIFE-paren trick forces eager compile). Same source.
- Service worker caches: V8 says SW Cache Storage uses different heuristics (a full code cache is created at install/store time rather than needing 2-3 loads). Text was truncated in my fetch; the 2018 blink-dev "CacheStorage Code Cache Hint" thread and Chrome 64+ confirm code cache generation for cache.put scripts. https://v8.dev/blog/code-caching-for-devs , https://groups.google.com/a/chromium.org/g/blink-dev/c/exoGLTG8m-c/m/5EUdD5zYBQAJ
- blob: URLs: Chromium's generated code cache gates on URL scheme (originally http(s), chrome, chrome-untrusted; embedders may register extra schemes) and rejects writes for non-enabled schemes and for opaque-origin locks. https://chromium.googlesource.com/chromium/src/+/ee57f57504a32463eca94fac09fc4788dacb7bd2/content/browser/code_cache/generated_code_cache_context.cc , https://gitcode.com/openharmony-tpc/chromium_src/blob/master/content/browser/renderer_host/code_cache_host_impl.cc , https://ayakael.net/mirrors/electron/commit/9aa73abe781ae5da01ac50e9165330722806d1d9
  - Conclusion (INFERENCE, no source states it directly): blob: script URLs are most likely NOT on-disk code-cached, and a blob URL is new every page load anyway so it has no stable key. The in-memory Isolate cache (keyed by source text) may still help within the same renderer process. Test with chrome://inspect or `performance` traces before relying on it.
  - Same-origin SW-served scripts have a real http(s) URL, so they are eligible for the disk code cache. Ours is a different story if the SW response is synthesized: whether synthesized (non-Cache-Storage) responses get a code cache is UNVERIFIED; serving from `cache.match()` is the documented path.
- Content-hash keyed caching of rewritten output: no proxy found publishing this. Storage options: Cache API (best, ties to code cache, streams), IndexedDB (blobs ok, more overhead), OPFS (fast sync handles in workers, good for large files). Chrome ships separate quota per origin; storage on a Chromebook is typically ample but can be evicted under pressure. Specifics of OPFS vs Cache API speed: UNVERIFIED.
- Module scripts via blob: relative imports inside a blob module do not resolve against a real path, so import maps or rewriting to absolute blob URLs is needed; each blob is a separate fetch-less module graph node. UNVERIFIED as a perf point; behaviour follows the URL spec.

What this means for us: key rewritten script output by sha256(source) (+ rewriter version) in Cache API/IDB so second visits skip the multi-MB rewrite entirely; that is the cheapest, safest win. Code-cache benefits need real http(s) URLs, i.e. the SW lane serving from Cache Storage, not blobs.

## 4. WISP, WISP v2, multiplexing, WebTransport, epoxy vs libcurl.js

- Wisp v1 (spec 1.2): one WebSocket carries many TCP/UDP streams. CONNECT, DATA, CONTINUE, CLOSE packets; stream IDs uint32 little-endian. Client may send data right after CONNECT without waiting (saves a round trip). Server buffers per-stream with a fixed buffer size; CONTINUE packets carry remaining buffer for flow control (TCP only). https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/v1/protocol.md
- Wisp v2 adds a handshake step for protocol extensions, password and key auth, MOTD, etc. No v2 feature is aimed at throughput in the summary I retrieved; I did not read v2 protocol.md in full. https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md , https://github.com/MercuryWorkshop/wisp-protocol/blob/v2/protocol.md
- epoxy-tls extension enum seen in its config: Udp, Motd, Wispnet. https://docs.rs/wisp-mux/5.1.0/src/wisp_mux/lib.rs.html
- Head-of-line blocking: all Wisp streams share one TCP/WebSocket, so one lost packet stalls every stream. WebTransport/QUIC avoids this at the transport layer, but a TCP tunnel over it re-adds HOL inside each stream. https://discourse.wicg.io/t/webtransport-proposal/3508 , https://arxiv.org/pdf/2102.07527
- Mitigation without WebTransport: open 2-4 parallel WebSockets (several Wisp sessions) and spread streams across them. Not documented by the projects; UNVERIFIED as a measured win.
- libcurl.js: libcurl in WASM, TLS 1.3, HTTP/2 multiplexing, connection reuse, Brotli and gzip, works in workers, 552 KB compressed, custom transport support, independent sessions. https://raw.githubusercontent.com/ading2210/libcurl.js/main/README.md
- epoxy-tls: Rust client compiled to WASM with rustls for TLS inside the WASM, plus Rust Wisp library and "performant" Wisp server. https://raw.githubusercontent.com/MercuryWorkshop/epoxy-tls/multiplexed/README.md
- No published epoxy-tls vs libcurl.js benchmark found. UNVERIFIED which is faster; both do TLS in WASM on the same thread unless moved to a worker.
- Wisp UDP is mandatory in v1.2 spec text, relevant only for QUIC/DNS, not for us.

What this means for us: moving libcurl.js into a Web Worker (it explicitly supports workers) takes TLS/HTTP off the page thread for free. Server-side: Rust epoxy-server or wisp-js; WebTransport is not an easy win for TCP tunnelling. Run our own libcurl-vs-epoxy bench on the Chromebook; none exists publicly.

## 5. Image pipeline on 2 vCPU / 2 GB (sharp / libvips)

- imgproxy benchmark (Apr 2024), c7i.large 2 vCPU Xeon, 4 GB, resize to fit 512x512, DIV2K images (about 2K source), 2 virtual users: WebP q75 about 22 req/s (imgproxy, libvips), Graviton3 26 req/s; AVIF q65 at max speed setting about 13 req/s (Xeon), 17.8 req/s (Graviton3). Throughput is with 2 concurrent workers, so per-image latency is roughly 90 ms (WebP) and 150 ms (AVIF) wall-clock per request on 2 cores. https://imgproxy.net/blog/image-processing-servers-benchmark/
  - AVIF here used the fastest encoder speed; at default/slow speeds it is far slower (imagor without a speed setting managed 1.6 req/s, about 1.2 s each).
- Third-party blog: WebP q80 about 0.19 s vs AVIF q63 about 1.30 s per image (about 7x), on a production server. https://dev.to/serhii_kalyna_730b636889c/i-benchmarked-17-image-conversions-on-my-production-server-some-results-were-not-what-i-expected-1j4f (blog, secondary)
- Another blog: WebP about 90 ms, AVIF (libaom default) 1 to 4 s, AVIF peak RAM about 2.5 GB vs about 200 MB for WebP, for a large (4000 px) image. https://dev.to/serhii_kalyna_730b636889c/avif-encoding-speed-the-numbers-nobody-talks-about-a2h . A 2.5 GB peak would OOM a 2 GB box: UNVERIFIED for sharp specifically, but a real risk to test.
- PkgPulse guide figures for sharp on an M2 Mac: 4K to 800 px about 50 ms, WebP about 40 ms, AVIF about 200 ms; another page by the same site says about 18 ms per JPEG-to-WebP resize at 100 images. Figures disagree; treat as order of magnitude only. https://www.pkgpulse.com/guides/sharp-vs-jimp-2026
- Rule of thumb from these (UNVERIFIED, extrapolated): JPEG decode with shrink-on-load plus resize to about 1000 px plus WebP about 30 to 100 ms CPU per typical photo on a 2 vCPU cloud core; AVIF 5 to 15x that. Sharp's own `sharp.concurrency(1..2)` and `sharp.cache(false)` limit RAM.

What this means for us: use WebP (effort 2 to 4) only, skip AVIF on a 2 vCPU box; budget about 10 to 20 images/s total, so cache results by (url, width, quality) and serve cached bytes. Decode on Chromebook is cheap, the cost on the device is mainly libcurl transfer plus postMessage copies (use transferable ArrayBuffers).

## Summary ranking for a slow-Chromebook in-page proxy (our judgement)
1. Content-hash cache of rewritten scripts (Cache API/IDB): skips repeat rewrite cost.
2. Move libcurl.js into a Worker; transfer ArrayBuffers, not copies.
3. Faster JS rewriter (OXC or similar in WASM) or skip rewriting of known-safe vendor bundles; measure first.
4. Progressive document display (iframe document.write streaming, or SW lane with ReadableStream).
5. Server-side WebP resize with cache; no AVIF.
