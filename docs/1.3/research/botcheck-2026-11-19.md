# Bot-check research for an honest browser-in-a-page proxy (2026-11-19)
Legend: [DOC] vendor documentation, [COMM] vendor/scraper blog or community (not authoritative), [UNVERIFIED] not confirmed.

## 1. What each challenge needs to work for a real human
- Cloudflare challenge pages: JS injected in the page evaluates the browser environment; non-interactive takes under 5 s, managed may ask a click. Must pass or the request is held. [DOC] https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/
- Turnstile widget lives in an iframe from challenges.cloudflare.com; a CSP or proxy blocking that frame gives Error 200500 "iframe could not be loaded". [DOC] https://developers.cloudflare.com/turnstile/ (client-side rendering and error pages)
- Turnstile sitekeys are bound to a hostname allowlist; running on an unlisted hostname gives Error 110200 "Unknown domain". Siteverify returns a hostname the site should check. "Any hostname" is Enterprise only. [DOC] https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/ and https://developers.cloudflare.com/turnstile/additional-configuration/hostname-management/any-hostname/
  - Implication: if the proxy page origin differs from the target hostname (e.g. blob:, proxy domain), widget may refuse or token fails the server hostname check. This is the biggest structural limit for client-side rewriting. Treat as expected failure, not a bug to defeat.
- Cloudflare WebView/troubleshooting list: JS disabled, no DOM storage/cookies, blocked challenges.cloudflare.com, User-Agent changing during the session; "some VPNs or proxies may interfere". [DOC] https://developers.cloudflare.com/turnstile/troubleshooting/challenge-solve-issues/
- Private Access Tokens: browser requests a token at /cdn-cgi/challenge-platform/.../pat/...; a 401 there is normal on devices without attestation, not a block. [DOC] same page. Privacy Pass/PAT needs OS-level attestation (Apple iOS 16+/macOS 13+); a web proxy cannot relay it for a different origin. https://developers.cloudflare.com/privacy-pass/ , https://datatracker.ietf.org/doc/rfc9577/ . Chrome/PACT status [UNVERIFIED] (single vendor blog).
- reCAPTCHA / hCaptcha: sitekey has a domain allowlist ("Invalid domain for site key"); siteverify returns hostname of where it was solved; sites may reject mismatches. https://docs.cloud.google.com/recaptcha/docs/verify , https://docs.hcaptcha.com . Iframes from google.com/recaptcha and hcaptcha.com need to load unmodified.
- postMessage between widget iframe and parent: not documented publicly in what I found. [UNVERIFIED] Do not rewrite or intercept messages from the vendor iframes; pass-through only. document.referrer / window.top / origin checks by vendors: [UNVERIFIED], assume checked.
- DataDome, PerimeterX/HUMAN, Akamai: no public requirement docs fetched. [UNVERIFIED] They rely on sensor JS plus cookies (_px*, datadome, _abck); same-origin, consistent headers, cookies kept.
- Honest action we can take: render vendor iframes untouched and un-rewritten (allow-list their origins in our CSP/rewriter), keep cookies and UA stable for the session, and show a clear "this site checks the page's hostname, it cannot work via a proxy" message when 110200/Invalid-domain errors appear.

## 2. cf_clearance
- Set when a visitor solves a challenge; default lifetime 30 min, Cloudflare recommends 15-45 min; site owner sets it via Challenge Passage; a few minutes of skew grace added. [DOC] https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/challenge-passage/
- Clearance is "time-bound (Interstitial) and behavior-bound (Precursor)". [DOC] https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/
- Binding to IP, UA, TLS/JA3: official pages found do NOT state it. Third parties claim all three. [COMM, UNVERIFIED] https://dev.to/bshahin/cloudflare-cfclearance-why-it-expires-and-how-to-stop-the-re-challenge-loop-do9 , https://www.zenrows.com/blog/cf-clearance . Plan as if bound to IP+UA.
- __cf_bm: set by Bot Management / Bot Fight Mode on end-user devices. [DOC] https://developers.cloudflare.com/fundamentals/reference/policies-compliances/cloudflare-cookies/
- Reuse: the real person can reuse their own cookie within lifetime if relay IP and UA stay the same. Same relay IP is only safe for one user at a time if binding is per IP; shared relay IPs mean other users' clearances may not fit. [UNVERIFIED]
- Honest action we can take: store cf_clearance per user per site in the proxy cookie jar, keep the same relay IP (sticky) and same UA string for that session, expire it at ~30 min, and re-prompt the human rather than anything automated.

## 3. Datacenter IP reputation
- Anti-bot systems map IP to ASN and score hosting ranges higher risk; burst traffic worsens it. [COMM] https://www.joinmassive.com/blog/why-ai-agents-get-blocked-on-datacenter-ips-and-how-to-fix-it , https://databay.com/blog/anti-bot-detection-explained (vendors that sell proxies, biased).
- Cloudflare verified bots: bot must self-identify (Web Bot Auth signature, published IP list with stable UA, or rDNS) and be non-abusive (obey robots.txt, reasonable rates). Categories are crawlers, monitors, agents, etc. [DOC] https://developers.cloudflare.com/bots/concepts/bot/verified-bots/policy/
  - New (July 2026) "Intermediary" label: agentic services run by many end users, treated with transitive trust. Whether a general web proxy qualifies: not stated; a proxy fits none of the listed behaviors. Verdict: treat as NOT a path for us. [partly UNVERIFIED]
- Honest actions that matter: set rDNS/PTR to a real hostname with matching forward record, publish an abuse contact page and abuse@ mailbox (also at the VPS provider's whois), per-user and global rate limits, block abuse (scanners, credential stuffing, scraping) early, one purpose per IP, no mixing free-user traffic on the paid relay IP. [COMM/common practice, UNVERIFIED as score inputs]
- Honest action we can take: separate relay IPs for paid vs public traffic, enforce rate limits, publish abuse contact + rDNS, and tell users datacenter IPs get more challenges.

## 4. TLS/HTTP2 fingerprint vs User-Agent
- JA3/JA4 are computed from the TLS ClientHello; shared across clients, used to profile clients, available in rules only to Enterprise Bot Management customers (so some sites use it, most cannot). [DOC] https://developers.cloudflare.com/bots/additional-configurations/ja3-ja4-fingerprint/
- Claim: Chrome UA with a non-Chrome TLS fingerprint is a strong bot signal. [COMM] https://scrapfly.io/blog/posts/how-anti-bot-detection-works , https://databay.com/blog/tls-fingerprinting-proxies , https://shifter.io/blog/tls-and-http2-fingerprinting-in-web-scraping . No vendor doc confirms it as a named trigger. Likely true for Enterprise Bot Management, DataDome, HUMAN, Akamai. [UNVERIFIED]
- HTTP/2 SETTINGS and header order are also fingerprinted [COMM] same sources. libcurl differs from Chrome on both.
- Honest fix without spoofing: truthful UA. Options: (a) send an honest UA token that says what we are (browser-like but identifying the proxy/client, e.g. keep browser name out of it) and accept more challenges; (b) forward the real browser's UA and client hints and document the mismatch as a known limitation; (b) is a grey area since the stack is not Chrome. Our rule (no fingerprint spoofing) points to (a) or to documenting. Decision for Boss. Do not adopt curl-impersonate.
- Honest action we can take: ship an honest UA suffix on relay requests (e.g. "... LimitlessProxy/x.y"), log which sites challenge more with it, and show "this site blocks non-browser TLS clients" in the failure explanation.

## 5. Google sign-in through proxies
- Google secure-browser policy prohibits OAuth requests in embedded webviews; blocked with disallowed_useragent. Reasons: MITM risk (intercept/alter requests, inject scripts, read cookies). https://developers.googleblog.com/en/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/ and policy https://developers.google.com/identity/protocols/oauth2/policies#browsers
- Google Account help: may block sign-in from browsers that lack JS, have unsupported extensions, are controlled by automation, or are embedded in another application. https://support.google.com/accounts/answer/7675428
- 2020 guidance on blocking less secure browsers/CEF/embedded IE. https://developers.googleblog.com/2020/08/guidance-for-our-effort-to-block-less-secure-browser-and-apps.html
- A page that rewrites cookies/location and proxies Google's login is exactly the MITM pattern; no honest workaround. Also passkeys/WebAuthn are bound to the real origin, so they will not work through a proxy [UNVERIFIED].
- Honest action we can take: detect accounts.google.com and show "Google does not allow sign-in through proxies or embedded browsers; use your normal browser for Google sign-in", cite the policy link; never try to bypass.

## 6. Measuring challenge rate without bypassing
- Method: for each site in a fixed list, one real-browser-like probe (our own client, honest UA) with a request per site at a low rate (e.g. 1 per 10 min), no retries after a challenge, respect robots.txt and ToS notes, run from the same relay IPs real users use.
- Classify only by passive signals; do not try to pass the challenge. Detectors:
  - Cloudflare: response header `cf-mitigated: challenge` [UNVERIFIED, commonly documented], HTTP 403/503 with body containing `/cdn-cgi/challenge-platform/` or title "Just a moment..."; set-cookie __cf_bm.
  - Turnstile widget: script src challenges.cloudflare.com/turnstile; hCaptcha: hcaptcha.com/1/api.js; reCAPTCHA: google.com/recaptcha/api.js or enterprise.js.
  - DataDome: `datadome` cookie, captcha-delivery.com in body; HUMAN/PerimeterX: `_px` cookies, px-cdn / perimeterx.net, "Press & Hold"; Akamai: `_abck`, `bm_sz` cookies, 403 "Access Denied" with reference ID. [COMM/UNVERIFIED patterns]
- Record per site per day: status code, vendor class, challenge shown yes/no, time. Compute rate = challenged / probes, split by relay type (paid VPS vs public relay) and UA variant (honest vs forwarded). Alert on spikes (may mean our IP got flagged).
- Pair with a human-in-the-loop sample: staff open the site in the proxy and record "solvable / not solvable", with the reason code (110200, 200500, loop).
- Honest action we can take: build a nightly low-rate probe that only classifies and writes a per-site "works / needs human check / cannot work" table feeding the in-app explanations.
