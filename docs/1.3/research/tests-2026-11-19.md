# Research: faster, less noisy release gate on one VM (2026-11-19)
Marks: [V] = seen in a fetched search result summary, [U] = unverified / my inference.
Note: sources below come from search-result summaries, not full page reads.

## 1. Comparing two builds with fewer runs
- Tachometer (Polymer/Google) runs A and B interleaved (round robin) on one machine, fresh browser profile per iteration,
  so drift hits both equally. Reports a 95% CI of the percent difference. Default min 50 samples, then auto-samples
  until the CI resolves a chosen threshold (e.g. "is B 10% slower?") or a timeout expires; `--timeout=0` turns auto-sampling off. [V]
  https://github.com/google/tachometer
  https://nolanlawson.com/2024/08/
  https://www.bram.us/2021/10/15/tachometer-statistically-rigorous-benchmark-runner-for-the-web/
  Caveat: if the true difference sits near the threshold, it never converges; the timeout decides. Needs a "can't tell" outcome. [V]
- benchstat (Go): Mann-Whitney U test, alpha 0.05, prints "~" when not significant. With n=4 vs m=5 the lowest possible
  p is 0.079, so you cannot reach significance; 5 vs 5 can (p=0.008 when fully separated). Maintainers suggest 10-20 runs
  when noisy. [V]
  https://golang.org/issue/19634
  https://golang.org/issue/23471
  https://go.googlesource.com/perf/+/HEAD/benchstat/delta.go
- Chromium Pinpoint: compares two sample sets with Mann-Whitney U (and KS) plus a dual-threshold rule giving
  Same / Different / Unknown; "Unknown" triggers more runs (adaptive sampling = sequential testing). [V]
  https://skia.googlesource.com/buildbot/+/main/pinpoint/docs/ai_generated_documentation.md
  https://skia.googlesource.com/buildbot/+/5e5efc5f8a30/pinpoint/go/compare/compare.go
- Mozilla Perfherder: t-test on alerts (threshold changed over time; MWU was discussed), default 2% alert threshold per test,
  sheriffs add retriggers for noisy tests; very noisy tests get dropped. [V, historical]
  https://wiki.mozilla.org/TestEngineering/Performance/Sheriffing/Alerts
  https://wiki.mozilla.org/TestEngineering/Performance/Sheriffing/Noise_FAQ
- Lighthouse CI: aggregates N runs per URL (default 3) by median/optimistic/pessimistic; Lighthouse docs say the median of 5
  is about 2x as stable as one run. Docs disagree on default aggregation: check the installed version. [V]
  https://github.com/GoogleChrome/lighthouse/blob/master/docs/variability.md
- Why median-with-fixed-thresholds flakes for you [U, standard stats]: with 7 reps and per-row "10% and 100 ms" cut-offs, you run
  hundreds of row-level tests; some false fails per run is expected. Per-row pass/fail needs multiple-comparison control.
- Rep counts: 5 vs 5 is the floor for MWU at 0.05; 10 per side is the common practical figure; Tachometer wants 50 for tight CIs.
Suggested change for our gate:
  - Run base and candidate interleaved (B1 C1 B2 C2 ...) in one process/stack, not "all base then all candidate".
  - Per row, bootstrap CI of the median difference (or MWU) instead of a plain median compare; fail only if the CI lower bound
    is above +10% AND above +100 ms. Three outcomes: pass, fail, inconclusive.
  - Adaptive: start 5 reps/side; stop early on clear pass (CI upper bound under threshold) or clear fail; only add reps
    (up to ~12) for inconclusive rows. Most rows should stop at 5.
  - Gate on a small set of headline rows (e.g. fixtures cold+warm per project), not every row; report the rest as advisory.
  - Rerun only failing rows once before failing the release (cheap confirmation).
  Estimated saving [U, my arithmetic]: 39 min at 7 reps/build ~ 5.5 min per rep-pair set; going to 5 interleaved reps that
  mostly stop early gives roughly 25-30 min; dropping the separate base build rebuild is extra if base results are cached per sha.

## 2. Noise reduction on one Linux VM
- Lighthouse variability doc: other processes on the machine cause CPU/memory/network contention; do not run several instances
  at once; prefer dedicated hosts, burstable instances are volatile; use median of repeats; throttling only partly helps. [V]
  https://github.com/GoogleChrome/lighthouse/blob/master/docs/variability.md
- Request-level DevTools/CDP network throttling is an approximation (delay applied once response is received, acts like a
  minimum duration). Packet-level (OS) throttling is the accuracy reference but is system-wide and can add variance. [V]
  https://www.debugbear.com/blog/network-throttling-methods
  https://www.debugbear.com/blog/chrome-devtools-network-throttling
  https://catchpoint.com/blog/full-throttle-comparing-packet-level-and-devtools-throttling
  https://github.com/GoogleChrome/lighthouse/blob/master/docs/throttling.md
- CDP `Emulation.setCPUThrottlingRate` is a slowdown factor on the page's main thread. The claim that it does not apply to
  workers was NOT confirmed by search. [U] Test: time a busy loop in a worker with and without throttle.
  https://chromedevtools.github.io/devtools-protocol/1-3/Emulation
- Other items asked about, no source found, general knowledge [U]:
  - `taskset`/`docker --cpuset-cpus` pins the browser and the stack to disjoint core sets (e.g. browser 0-3, nginx/relay 4-5,
    the rest for the OS). Reduces scheduler migration noise; on a VM the vCPUs may still share host cores (steal time).
  - Turbo/frequency cannot be controlled in a VM; check `steal` in `vmstat 1` and drop reps that ran with steal above ~2 percent.
  - Chrome flags often used for stability: `--disable-background-timer-throttling`, `--disable-renderer-backgrounding`,
    `--disable-backgrounding-occluded-windows`, `--disable-extensions`, `--disable-component-update`, `--no-first-run`.
    Fresh profile per run (Tachometer does this).
  - Run nothing else on the VM during the speed gate (do not overlap with e2e, prebuild timers, backups).
  - Because the CDP network throttle is request-level, keep fixtures local so network jitter is zero; public sites in the
    speed gate add uncontrollable variance: move them to the real-site suite or make them advisory.
Suggested change for our gate:
  - Pin: browser to a fixed cpuset, compose services to another via `cpuset` in compose; stop competing timers during the run
    (pause flag for prebuild exists per your docs).
  - Log steal time and load per rep; discard/redo reps with high steal.
  - Make public-site rows advisory in the speed gate.
  Saving: mainly fewer false fails (re-run cost avoided, ~39 min per false fail); little raw time.

## 3. Playwright speed
- `--only-changed[=ref]` runs only test FILES changed vs a git ref (default HEAD); it is file-level, not dependency-aware, so
  a changed app source does not select tests; needs the base ref present locally (shallow clones fail). [V]
  https://playwright.dev/docs/test-cli
  https://dev.to/playwright/iterate-quickly-using-the-new-only-changed-option-55m2
- Playwright runs headless on `chromium-headless-shell` by default since 1.49; "new headless" (channel `chromium`) uses the full
  binary. The shell is lighter; no authoritative benchmark found, vendor claim only that new headless costs "slightly" more. [V]
  https://github.com/microsoft/playwright/issues/33566
  Keep the headless shell for e2e. For the speed gate, keep ONE mode for both builds; changing mode changes baselines.
- Not covered by search, general knowledge [U], verify at https://playwright.dev/docs/test-parallel and /test-sharding and /test-auth:
  - Workers: default is half the logical cores (4 on 8 vCPU). With 7 GB free RAM, 4 Chromium workers is already near the
    limit; try `--workers=50%`/5 vs 4 and measure; more workers on 8 vCPU often yields timeouts, not speed.
  - Sharding is for multiple machines; on one VM it gives nothing beyond workers.
  - `storageState` auth: do login once in a setup project (or globalSetup), reuse the JSON; avoids a login per test.
  - Trace/video/screenshot off in gate runs (`trace: 'off'`, `video: 'off'`), or `retain-on-failure` only.
  - Tag with `@smoke`/`@affected` and use `--grep`; derive the affected set from changed paths (a path-to-tag map in the repo).
  - Reuse a built static output/prebuilt image for both e2e and speed gate; do not rebuild per project.
  - e2e and speed gate must never run at the same time (noise): run them in sequence, e2e first.
Suggested change for our gate:
  - e2e: tiered. Full 460 only nightly/for Minor+; for Patch/Hotfix run `@smoke` + tests selected by changed-path tags.
  - Tune workers by measurement (try 3, 4, 5 on a 50-test sample); disable trace/video; use storageState.
  Saving [U]: 25 min -> roughly 8-12 min for a tagged subset (about 40 percent of tests); a worker tune is typically 0-20 percent.

## 4. Docker compose stack startup
- `docker compose up -d --wait` blocks until services are running or, with a healthcheck, healthy. Services without a
  healthcheck count as ready once running (so add healthchecks to nginx, auth gate, relay, fixture sites). [V]
  https://maciejwalkowiak.github.io/blog/docker-compose-waiting-containers-ready/
  https://oneuptime.com/blog/post/2026-02-08-how-to-use-docker-compose-healthcheck-configuration/markdown
- `healthcheck.start_interval` polls fast during `start_period` (needs Compose 2.20.2+, Engine 25+); a regression was reported
  in Compose 2.26.1 (worked in 2.24.5). Check your version. [V]
  https://github.com/docker/compose/issues/11683
- No source found on tmpfs or keep-up-vs-recreate; general guidance [U]:
  - Keep the stack up between the base and candidate runs and swap only the changed service (`up -d --no-deps <svc>`); recreate
    only when images change. Use prebuilt images (your prebuild timer already does this) so there is no build step.
  - Use `tmpfs` for any scratch/DB/log dirs of the rehearsal stack to remove disk jitter.
  - Warm-start: run one discarded warm-up pass after (re)start so first-run image/page-cache effects are not in the data.
Suggested change for our gate:
  - Healthcheck + `up -d --wait` with short `start_interval`; one stack for both builds (base and candidate as two upstreams
    or two services side by side, interleaved), tmpfs scratch, one discarded warm-up.
  Saving [U]: stack restarts are probably 1-3 min each; the bigger win is that one stack makes true ABAB interleaving possible.

## 5. Real-site suite (42 sites x 3 reps, 1 worker, ~1 h)
- No authoritative source found for per-site rate limits on public sites. General practice [U]:
  - Parallelism across DIFFERENT hosts is safe; never run more than 1 concurrent request-stream to the same host.
    With 42 distinct sites, 3-4 workers each owning disjoint sites keeps per-site load identical to today.
  - Order the 3 reps across sites (site1 r1, site2 r1, ... then r2) so a host gets minutes between hits instead of back-to-back.
  - Pass/fail checks (page loads, key element visible) are not timing-sensitive, so noise from parallel workers does not matter;
    do not run it at the same time as the speed gate.
  - DNS: run a local caching resolver (dnsmasq/unbound, or systemd-resolved cache) on the VM so repeat lookups are local; Chromium
    also has its own host cache. Expect small gains (tens of ms per navigation).
  - Fail on 2 of 3 reps (retry-once policy) rather than 3 of 3 strict, and treat 429/403/captcha as "blocked", not "broken".
  - Skip a site after one clean pass in rotation: run a rotating third of the sites per night, all 42 over 3 nights, plus
    full runs only for Minor/Major (judgement call, needs Boss decision).
Suggested change for our gate:
  - Workers 4, site-sharded (one site per worker at a time), reps interleaved across sites, retry-once.
  Saving [U]: 1 h -> about 15-20 min at 4 workers (memory permitting: 4 Chromium contexts, check the 7 GB free).

## Combined budget sketch [U]
  e2e tagged subset ~10 min + speed gate adaptive ~25 min + real-site 4 workers ~15 min = ~50 min; run real-site only on
  Minor/Major or on a rotating subset to land under 45 min. Memory: never overlap suites.
