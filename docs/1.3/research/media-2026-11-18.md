# Image and video research (G1, G2, I1 to I3; research 2026-11-18)

## 1. Image resize on a 2-core VPS

Important finding first: the image lane already exists in 1.2.0 (OFF): gate `src/img/lane.ts`, sharp, WebP quality 75 for JPEG/PNG of 30 KB or more, 1 GB disk LRU for 24 h, container `cpus: 0.75`, 2 parallel encodes, 32 queued then 503, 300 images a minute per member, SSRF guard (`~/Browser/docs/1.2/IMGLANE.md`). G2/N6 is therefore "add resize to shown width" on top of a built lane, not a new service. Today the lane serves the original dimensions (`w` and `s` modes only choose WebP or not). `srcset`, CSS `url()` images and video posters still take the libcurl path (IMGLANE "Not done").

Measured by us (SPEED-AUDIT 1.3, Steam capsules, sharp, one thread): WebP q75 same size 1.22 MB from 4.27 MB (-72 percent), 24.6 ms per image on the Gamble VM, 13.5 ms on the VPS-class CPU; WebP q70 max 683 px wide: 1.03 MB, 11.7 ms on VPS-class; AVIF q50: 0.77 to 0.99 MB (-77 to -82 percent), 101 ms on VPS-class. One VPS core is about 74 WebP images per second. Resizing down reduces both bytes and WebP encode time (q70/683 px is 13 percent cheaper than q75 at original size).

Outside facts:
- sharp is libvips: only small regions of the image are held in memory at once (https://sharp.pixelplumbing.com/ , via search summary). Its own benchmark (AWS c8a.xlarge, 4 vCPU, JPEG 2725x2225 decode, resize to 720x588, re-encode): sharp about 83 to 90 operations per second, about 24 to 26 times jimp (pure JS) and 4 times ImageMagick/gm in the same table (https://sharp.pixelplumbing.com/performance). Machine differs from ours; ratios are the point. Greater performance "with caching enabled and 8+ core machines", "the I/O limits of the relevant (de)compression library will generally determine maximum throughput" (same page).
- Concurrency: libuv thread pool default 4 (`UV_THREADPOOL_SIZE`), libvips threads per image default to the CPU count, except glibc Linux without jemalloc or `MALLOC_ARENA_MAX` where it is 1 to cut memory fragmentation; set `MALLOC_ARENA_MAX=2` or 4 (https://sharp.pixelplumbing.com/performance). On our 2 vCPU with a 0.75 CPU limit: `sharp.concurrency(1)`, `UV_THREADPOOL_SIZE=2`, `MALLOC_ARENA_MAX=2` are the settings to test. The libvips operation cache defaults 50 MB, 20 files, 100 items (https://sharp.pixelplumbing.com/api-utility): set `sharp.cache({memory: 50})` or lower in a 2 GB box.
- Output defaults: WebP quality 80, effort 4 (0 to 6); AVIF quality 50, effort 4 (0 to 9) (https://sharp.pixelplumbing.com/api-output). Lowering AVIF effort to 2 to 3 is the only way AVIF might fit the budget; our earlier number at the default shows 8x WebP's CPU.
- Resize on load: libvips can shrink JPEG while decoding (JPEG shrink-on-load) so decoding a large JPEG to a small size is cheaper than decode-then-resize. The sharp docs page for this (`fastShrinkOnLoad` and `jpeg` options) was in the output page; exact speed gain: not measured here, a one-hour measurement on the Steam sample would settle it (candidate for G2 slice 1).
- Blog benchmarks of WebP against AVIF (secondary, methods unclear): AVIF libaom about 1 to 4 s at 1080p and up to 2.5 GB RAM against WebP about 90 ms and 200 MB (https://dev.to/serhii_kalyna_730b636889c/avif-encoding-speed-the-numbers-nobody-talks-about-a2h); AVIF about 7x slower than WebP and 68 percent smaller than JPEG on 50 real photos (https://dev.to/serhii_kalyna_730b636889c/i-benchmarked-17-image-conversions-on-my-production-server-some-results-were-not-what-i-expected-1j4f). Our own measured 8x CPU agrees with the 7x figure. Conclusion stays: WebP only on the VPS; AVIF is not worth it on 2 cores (SPEED-AUDIT section 5). A shared cache changes the math only for hot images (each encode once, served to many): a possible later use is nightly AVIF for the top-site images during idle hours (G5). Not recommended before G6 shows hit rates.
- Competing tools (imgproxy, imagor, others): a benchmark page exists (https://imgproxy.net/blog/image-processing-servers-benchmark/) but is a vendor page and was not read in this run: "not found" for neutral numbers. sharp/libvips is already in the lane; no reason to switch.

Memory on 2 GB: a 50 megapixel limit (already in the lane) decodes to about 150 MB RGB before shrink-on-load helps; limit concurrent decodes to 2 (already) and consider lowering to 25 megapixels for the resize mode. Memory under real load: not measured.

Design for G2 on the existing lane (small): add a target width to the path (`/i/<token>/<mode><width>/<url>`), width taken from the displayed layout width times devicePixelRatio, rounded up to a bucket (240, 360, 480, 720, 960, 1280, 1920) so the cache keeps few variants per image; never upscale; skip images under 30 KB or smaller than the bucket; the cache key is the SHA-256 of mode + bucket + URL (today mode + URL). Variants per image: at most 3 in practice. App side: the frame runtime already tries `LB_imgLane.url(abs)` in `loadMedia`; it needs the element's rendered width (available at load for visible images via `getBoundingClientRect` or `sizes`), falls back to no width. Image lane on/off is per member (`limitless:imglane:v1`).

G1 (visible first): the app already pre-warms only the first `LB_PREWARM_TOP` (6) images (`lazyPrefetch`) and sets lazy loading near the viewport (`lazyImg`). What G1 adds is a blurred placeholder and ordering by distance from the viewport: use `IntersectionObserver` with a rootMargin, `loading=lazy` semantics, and `fetchpriority`. A tiny placeholder needs a source: the VPS lane can return a 24 px blurred WebP (about 300 bytes) as a `p` mode, or the page can show a solid average colour computed from the first bytes (no server). Standard placeholders are a web pattern (BlurHash/LQIP, secondary): the lane variant is cheaper to build here (1 d) and only for Cardinal+; the all-tiers version (Boss: "all") must be client only: ordering plus a neutral skeleton colour, no blur data. Plan: G1 client-only ordering and skeleton for everyone, blur from the lane for paid.

Test: tags `images` (Steam, Reddit r/pics feed, Pinterest, Imgur-style galleries, Wikipedia commons; plus a fixture page with 200 images of known sizes and an infinite scroll). Measure: bytes received, images shown at 1 s and 3 s, long tasks. Failing test first: a fixture page where the displayed width is 300 px and the source is 1920 px: expect the request to carry the 360 bucket.

## 2. How YouTube requests media (what public sources say) and what I1 needs

What is publicly documented: nothing official was found. Community reverse-engineering (secondary, flagged by their own authors as "may change without notice"):
- Newer YouTube delivery is SABR: a session-style protocol on a `serverAbrStreamingUrl` where the client repeatedly POSTs its state (selected formats, buffered ranges, player time, a continuity token) and the server answers with a UMP body, a stream of typed length-prefixed parts: format metadata, media headers and segments, and instructions such as next-request policy and a redirect (https://priveetee.github.io/Docs-PipePipe/extractor/sabr.html, https://priveetee.github.io/Docs-PipePipe/developer-guide/sabr-protocol.html, library https://github.com/LuanRT/googlevideo, https://jsr.io/@luanrt/googlevideo/doc/sabr-stream/).
- The same source says playback of some videos is gated by a server-side proof-of-origin token and that a legitimate integration must run the real client; it is not something we touch. We do not parse, replay or re-implement SABR: the page's own player does all of it, and our job is transport only.
- Older plain progressive/DASH requests used `videoplayback` URLs with byte-range parameters: no official specification found ("not found"); our own capture shows 12 `videoplayback` fetches with median 3.9 MB (max 5.4 MB) and median 2.5 s to response headers (SITES-MEDIA 3.6).

What our code does today (SITES-MEDIA section 3.6 and SPEED-AUDIT item M): YouTube watch page fetched 43.7 MB of media while 2.9 MB was appended (18 `appendBuffer` calls), i.e. 15x; whole responses are delivered to the frame late, and aborted requests keep costing bytes. The player asks for large look-ahead ranges; our transport buffers each response completely before handing it over, with `max_message_size = 65536` WISP frames available. The existing pieces: `queueFetch` and `doFetch` (`app/main.js` 5661, 5993), a `noBodyCap` rule for range and media extensions (5878), 206 slicing when the server ignored Range (6254), `videoSock` (shared `v/` socket for video hosts), `videoCap` (YouTube quality range every 1.5 s), `oneVideo`.

What I1 "fetch only what plays" needs, in order of cost:
1. Stream bodies. Hand `fetch` and XHR bodies to the frame in 64 KB steps as `ReadableStream` chunks (a `stream` message type already exists at the runtime, line 6945 per SITES-MEDIA) so MSE appends the first chunk early, and when the player aborts a request the read stops and the socket slot is released. This alone removes most of the 43.7 vs 2.9 MB waste if the waste comes from late aborts (hypothesis: the doc says [G] guess, to be proven with a capture counting bytes read after abort). Effort 3 to 4 d, risk medium (video start regressions), tags `video`.
2. A Range-aware path in `doFetch` that forwards the player's own `Range` header and returns 206 properly (today `Range` bypasses the response cache by design; it passes through, plus the slicing fallback).
3. Quality at the shown size: `videoCap` already clamps by plan; add a size-based cap: player size on screen (a 640 px wide player does not need 1080p) through `setPlaybackQualityRange` for YouTube and source choice elsewhere. Chromebook default 480p start (I3) is a one-line change of the cap for that device class.
4. Do not prefetch beyond what plays: the player's look-ahead is the player's choice; we can reduce it only by a quality cap or by the page's own settings. Not by editing the protocol.
5. Executive relay buffering (I3): the VPS reads ahead of the member's pull from the origin so the next range is ready; this needs a media cache keyed by (URL, range) and breaks for token-bound URLs. Honest view: low hit rate (each video is watched by few members) and the VPS counts the data twice on the 5 TB meter; the real gain is latency, not bytes. Defer until streaming (1) is measured.
6. Cache: googlevideo segments are not shared across members in practice (per-session URLs and tokens, secondary evidence from the SABR docs); do not cache video on the VPS.

I2 (thumbnails through the image lane): thumbnails are ordinary images (`i.ytimg.com`), public; the lane handles them as soon as the runtime sends them through `LB_imgLane.url`. Posters (`<video poster>`) and CSS `background-image` need the lane hooked in the same places (not done today). Effort 1 d once G2 exists. Test tags `video`, `images` (YouTube home grid).

Order for video: stream bodies (I1 part 1) is the single biggest data and start-time win in the plan; it is client-side and for all tiers, so it does not need the VPS. It should probably come before the image resize.
